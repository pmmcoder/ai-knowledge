# 和 AI 一起写代码：从模型原理到工程师定位

> 这不是操作手册，是一套从"模型到底是什么"推导出来的思考方式。
> 核心判断只有一句：**AI 没有改变"什么是正确的代码"，它改变的是"生产正确代码的成本结构"。** 代码生成的边际成本被大幅压低，但复杂度不会消失，只会转移——于是工程师的核心价值，从"制造代码"转向"驾驭复杂度"。这不是效率提升，是范式转换。
>
> 全文顺着一条因果链走：先看清 AI 是什么（三个事实）→ 由此推出根本矛盾（验证成为瓶颈）→ 会反复撞上的具体机制 → 工程师围绕这个瓶颈的新定位与具体做法 → 系统和个体层面的应对 → 最后诚实交代这些原理何时不适用。与其背规则，不如理解这条链——规则会自己长出来，你也能自己判断它何时不适用。每个抽象结论都尽量配一个 Go 实例。

## 一、核心命题

AI 最容易制造一种错觉：只要模型足够强，工程师就能把需求交出去，等它返回代码。但真实项目里，代码从不是孤立文本——它连着历史包袱、业务规则、上线风险和生产事故。

所以真正有用的问题不是"AI 会不会写代码"，而是：**AI 降低了什么、没降低什么，以及这个落差把工程师推到了什么新位置。**

一句话立论，后文全部由它展开：

> AI 降低了代码的生产成本，但复杂度不会消失，只会转移。工程师的核心价值，从"制造代码"转向"驾驭复杂度"。

要理解这个转变为什么成立，得先看清楚这个工具本身是什么。

## 二、先想清楚 AI 到底是什么：三个决定一切的事实

### 事实 1：它是一个条件概率分布，不是一个有意图的工程师

模型在做的事，本质上是：给定你喂进去的上下文，采样"最可能出现的后续文本"。它没有目标、没有对错观、没有对后果的敬畏。把这一点想透，很多现象就不再意外。

一个必要的精确化：**这里说的是模型内核。** 你实际用的编码 agent，是围绕这个内核再套上工具调用、检索、命令执行、上下文管理、系统提示和权限控制的**工程系统**——它不是纯 LLM。外壳能约束、纠偏、甚至部分补偿内核的行为（这正是后面"构建验证带宽"和"安全护栏"的着力点），但改变不了内核"按概率续写"这个底层机制。本文三个事实讲的是内核；正因为它被外壳包着，你才既能利用外壳做验证，也要防外壳把内核的错误执行、放大到真实世界（命令、依赖、生产数据）。

**推论 A：它输出的是"最像对的"，不是"对的"。** 合理性（plausibility）和正确性（correctness）高度相关，但不是一回事。一段自信、流畅、格式漂亮的错误代码，对模型来说是完全正常的产物。

**推论 B：没有强约束时，它回归训练数据的"中位数写法"**——主流框架惯用法、网上最常见（因此往往过时或不安全）的模式。看得见的例子：你项目里错误处理有自己的约定，但你没在上下文里点明时——

```go
// 项目约定（它拿不到时不会主动用）：错误要带业务码、写进统一封装
return apperr.Wrap(err, apperr.CodeStockRevertFailed)

// 模型的默认产物：训练分布里最常见的 Go 错误写法
return fmt.Errorf("revert stock: %w", err)
```

两段都"对"，但第二段违背你的项目约定。模型不是不会写第一种，是**没有理由写第一种**——它落在分布边缘，而 `fmt.Errorf` 落在众数上。**推论很实际：你的上下文预算，要优先花在"你的代码库偏离主流的地方"，而不是它本来就会写对的部分。** 样板代码就是分布的众数，所以它写得又快又好；你的系统在分布边缘，所以它一到你的特有约定就开始猜。

**推论 C：**"让报错消失"常常比"修根因"概率更高。更可能的原因不是它偷懒、也不是那样"更短"，而是训练分布里"让测试过去"的样本大量本身就是删断言、放宽校验、加 `recover()` 这种表面修补。你若只说"把测试跑通"，就是在往它概率最高的那条路上推。（这段是对机制的推断，不是被证明的事实，但它比"它比较懒"更能预测你会遇到什么。）

> 有多常见？一项对 16 个代码生成模型、57.6 万段代码的分析发现，商业模型平均约 **5.2%** 的推荐包名是幻觉，开源模型高达 **21.7%**，累计出现 20 万+ 个不存在的包名——这正是"看起来对"与"真的对"分家的实测。（出处 3，含样本局限）

### 事实 2：AI 大幅压低了"生成"的边际成本，却没有等比例压低"建立独立可信证据"的成本

这是最重要、也最少被讲透的一点。要说精确：AI 也能帮你验证——生成测试思路、解释失败日志、补 property test、跑静态分析、做 diff review，这些都实实在在提效。但它压低的是**生成**的边际成本；而"建立**独立于生成通道**的可信证据"这件事，成本没有等比例下降。原因就在事实 1：让 AI 既写实现又当裁判，裁判和选手同源，你拿到的是一致性，不是独立性。所以，粗糙但方向正确的说法是——**写变快了几个数量级，"确信它对"却没有同步变快。**

**瓶颈整体转移到了验证与审查。** 硬推论：任何"提高生成量、却不同步提高验证能力"的做法，都是负收益。你不缺代码了，你缺的是"确信这段代码对"的能力。

这重新解释了"小步、小 diff"：不是因为小 diff 优雅，而是**验证成本随 diff 规模、以及你能否把它整个装进脑子而上升。** 一个大到你无法认真读完的 diff，产出的不是代码，是"一堆等你签字背书的风险"。

也解释了为什么"AI 写实现、又让 AI 写测试、然后它自己说通过了"是幻觉安全。看得见的例子：

```go
func RestoreStock(ctx context.Context, orderID int64) error {
    items, _ := repo.ItemsByOrder(ctx, orderID)
    for _, it := range items {
        stock.Add(ctx, it.SKU, it.Qty) // 无幂等：重复取消会重复加库存
    }
    return nil
}

// 模型顺手补的测试——它证明的是"当前实现的行为"，不是"正确的行为"：
func TestRestoreStock(t *testing.T) {
    seedOrder(t, 1001, item{SKU: "A", Qty: 2})
    _ = RestoreStock(ctx, 1001)
    require.Equal(t, 2, stock.Get("A")) // 绿。
}
```

测试是绿的，覆盖率也许还很好看。但"重复取消不能重复恢复库存"这条真正的业务规则**根本没进测试**。你并没有付出任何**独立的**验证成本，只是让它自证了一致性——**自洽 ≠ 正确。** 代码生成和测试生成来自同一个概率分布、同一份上下文偏见，它们可能在同一类边界条件上一起犯错。这比没有测试更危险，因为它给了你虚假的覆盖率。谁来定判据，决定了验证到底有没有发生（详见第五节·角色2）。

### 事实 3：你持有系统的全局不变量，它只有局部模式匹配

一个资深工程师真正值钱的资产，是脑子里那套**系统的不变量和失败模式**：并发下操作的先后、钱不能凭空产生或消失、这张表的迁移必须能回退、这个接口没权限的人绝对不能进。模型做的主要是**局部**的模式补全，它看不到、也不持有你这套全局约束。

接着上面的例子——为什么模型写不对 `RestoreStock`？因为决定"必须幂等"的那条不变量，**不在它能看到的局部上下文里**：

```go
// cancel.go —— 模型能看到的局部：一切看起来都合理
func (s *Service) Cancel(ctx context.Context, orderID int64) error {
    if err := s.setStatus(ctx, orderID, StatusCancelled); err != nil {
        return err
    }
    return RestoreStock(ctx, orderID)
}
```

而"取消可能被重复触发"这个事实，住在**另一处**——消息队列的 at-least-once 投递、前端的重复点击、超时重试。模型读 `cancel.go` 时看不到这些，于是它写出的局部合理代码，破坏了一条它视野之外的全局不变量。而且——**破坏时测试是绿的。**

**这才是"高风险清单"的真正原理**：危险程度 ∝ 一个改动依赖了多少个"它在局部上下文里看不见的全局不变量"。并发、权限、金额/库存/额度、数据迁移之所以危险，不是因为代码复杂，而是因为它们高度依赖这种全局约束。

**推论：分级不该按"任务难不难"，该按"这个改动要不要用到我脑子里、而它拿不到的那套不变量"。** 要用到，你就得亲自盯关键路径，或者把那条不变量显式写进上下文；用不到（纯样板、机械变换），才能真正放手。

### 三个事实的一句话概括

| 事实 | 一句话 | 它逼你负责什么 |
|---|---|---|
| 事实 1 | 它不是在思考，是在"续写" | 判断对错 |
| 事实 2 | 它把"写"变便宜了，却把"审"变贵了 | 控制生成规模 |
| 事实 3 | 它在看局部，你在守全局 | 守护全局不变量 |

右边这一列，正是第五节要展开的"新定位"。但在谈定位之前，先把事实 2 从"静态的成本对比"推到它的动态后果——这才是一切工程混乱的真正来源。

## 三、根本矛盾：生产带宽与验证带宽的剪刀差

事实 2 说的是一个静态落差。把它放到时间轴上，就变成一对此消彼长的量：

| 概念 | 定义 | 现状 |
|---|---|---|
| **生产带宽** | 单位时间内能产出多少代码 | 被 AI 显著放大 |
| **验证带宽** | 单位时间内能对多少代码建立**独立**的"确信" | 没有等比例放大，甚至因 AI 生成的陌生代码而变慢 |

（这对概念是本文用来分析的框架，不是行业既有术语。）过去两者大致匹配：写代码本身就带着思考，写和验证是同一拨人、同一个节奏，速度天然受限。现在生产带宽被显著放大，而独立验证带宽没有等比例提升。**两者的剪刀差，就是 AI 时代一切工程混乱的根源。**

这个剪刀差能统一解释很多现象：

- 为什么 AI 辅助开发一开始很爽，越到后面越失控？→ 生成量积累到一定程度，**验证债务**开始反噬。
- 为什么小 diff 是唯一可持续的方式？→ 它让验证带宽跟得上生产带宽。
- 为什么"让 AI 写代码又让 AI 写测试"危险？→ 那是在**伪造**验证带宽（事实 2 的自洽陷阱）。
- 为什么架构治理比以往更重要？→ 架构是在从系统层面**降低对验证带宽的需求**（详见第六节）。

于是"高效编码"的定义变了：

> 不是"单位时间产出更多代码"，而是"单位时间内让更多代码达到可信状态"。

瓶颈既然在"验"，工程师的能力就得围绕"验"重建。在讲怎么重建之前，先补三个你几乎每天都会撞上、且会直接冲击验证的具体机制。

## 四、三个你会反复撞上的具体机制

三个事实是"地基"。下面三个是地基之上、你几乎每天都会遇到的具体行为。它们的成因**不是同一个**，别都推给 RLHF：谄媚主要来自偏好训练（人类反馈会奖励"迎合用户信念"）；判据博弈是更普遍的目标/判据设计问题，比 LLM 更老，不必绑定某种训练方式；多步误差累积则来自状态传播与反馈循环。它们分别来自概率补全、偏好训练、目标设定和多步反馈循环的组合——共同点只是：都会直接冲击你的验证。

### 4.1 谄媚（sycophancy）：它倾向于附和你已经说出口的判断

有研究专门刻画了这一点：经过人类反馈训练的模型倾向于给出**迎合用户既有看法**的回答，而不是最真实的回答；甚至"人类和偏好模型都会在相当比例的情况下，更偏爱写得漂亮的谄媚回答而非正确回答"（出处 4）。

实操后果很重，尤其在排查 bug 时——**你先抛出的猜测，会污染它的诊断：**

```text
❌ 你：这个测试挂了，应该是 mock 没配好吧？帮我看看。
   模型：对，确实是 mock 的问题。你在 setup 里漏了 EXPECT()……（顺着你的猜测，
         给一个听起来很有道理、但可能完全跑偏的"修复"）

✅ 你：这个测试挂了，完整输出如下：[贴原文]。
     先独立判断根因，不要假设我下面这句对——我怀疑是 mock，但可能错。
     给出你的判断和依据。
```

原理直接决定用法：**问根因时，把你的猜测放到最后、并明确标注"这可能是错的"，或者干脆先不说。** 你越早说出结论，它越会替你的结论找理由。

### 4.2 自主循环里的误差累积：多步自主 = 错误滚雪球

当你让一个 agent 连续自主跑很多步（读→改→跑→再改……），每一步都以"可能已经错了的上一步"为条件继续。这里有个简单但残酷的算术：**若每一步独立正确的概率是 p，连续 n 步全对的概率约是 pⁿ。**

- 单步 95% 正确，听起来不错；连续 20 步全对只剩约 36%。
- 单步 99%，连续 50 步也只剩约 61%。

（这是概率上的分析论证，不是实测数字，用来说明趋势——真实场景里各步并不独立，错误还会相互放大。）这解释了为什么长时间无人看管的自主运行会**慢慢漂**离目标，以及为什么"它前面几步都对"不能推出"它第十步也对"。

实操推论：**回合要短、要设检查点。** 每隔几步就回到一个可验证的锚点（测试绿、diff 可读、状态可回滚），把 pⁿ 里的 n 压小。让它一口气跑五十步再回来看，等于把误差累积到最难拆解的时候才介入。

### 4.3 判据博弈（specification gaming）：你给的判据本身会被钻空子

"追求字面目标、而非你的真实意图"是个比 LLM 更老的问题——强化学习里叫 reward hacking / specification gaming，2016 年就被列为 AI 安全的核心问题之一（出处 5）。在 AI 编码里它以很具体的形态出现：**你说"让这个测试过"，它可能去满足判据的字面，而不是达成判据想表达的意图。**

```go
// 失败的测试：ParseAmount 应把 "1,000.50" 解析成以分为单位的 100050
func TestParseAmount(t *testing.T) {
    got, err := ParseAmount("1,000.50")
    require.NoError(t, err)
    require.Equal(t, int64(100050), got)
}

// 判据博弈式的"修复"——测试绿了，但函数是假的：
func ParseAmount(s string) (int64, error) {
    if s == "1,000.50" {
        return 100050, nil // 专门迎合这一个用例
    }
    return 0, errors.New("unsupported")
}
```

这不是编造的极端情况，是"让报错消失概率更高"（事实 1 推论 C）在有判据时的必然延伸。两条对策：

1. **判据要写意图，不只写用例。** 让它覆盖正常/边界/反例多组输入，而不是一个特例——一个特例，它就特判一个特例。
2. **判据的作者要独立于实现的作者。** 你（或先于实现、经你确认的测试）定判据；否则就是让被考核者自己出考卷。

## 五、工程师的新定位：围绕"验证瓶颈"重建能力

前面三节说清了"是什么"和"矛盾在哪"。现在落到"你该怎么做"。三个事实的右列，恰好长成三种新角色——它们不是三份工作，是同一个人在同一次改动里要同时扮演的三副面孔。

所有角色之上，有一个共同的底层姿态：

> **把每个 AI 输出当成"假设"，不是"结果"。** 你不是在"拿代码"，你是在"生成一批待验证的主张"。姿态从消费者切换成审查者——这一个心态转变，比任何 prompt 技巧都重要。

### 角色 1：意图的精确表达者（对应事实 1）

既然它只会朝"最像对"的方向续写、默认回归主流写法，那么产出"像对"还是"对"，极大程度上取决于你喂进去的上下文。你的工作不是写代码，是**用自然语言和约束，把概率分布重塑到"对的区域"**：

- 知道业务目标、系统设计原则、什么该包含什么该排除、"完成"的定义是什么；
- 上下文预算优先花在**你的代码库偏离主流的地方**（事实 1 推论 B），而不是它本来就会写对的样板；
- **把上下文当成"有损、且无持久"的工作记忆来经营。** 它跨会话没有记忆；会话内注意力也不均匀。早期研究发现关键信息落在长上下文**中间**时最容易被忽略（"Lost in the Middle"，出处 2）；这个"中间最差"的位置效应在新一代模型上已明显减弱——简单的定位召回（needle-in-haystack）甚至接近满分。但**"有效上下文"远小于"标称上下文"这件事并没有随之消失**：一旦要在长上下文里做推理或非字面关联，前沿模型到几万 token 仍会显著掉点（RULER、NoLiMa，出处 2）。所以：最关键的目标和证据放到它能用到的位置；**被否定的方案要显式清除**，否则它分不清"废案"和"现行计划"；同一问题纠正两轮还不对就重开。（Anthropic 官方也把"上下文填满→性能下降"列为使用 Claude Code 的头号约束，出处 8。）

### 角色 2：验证体系的构建者（对应事实 2）

既然验证是瓶颈（第三节的剪刀差），你的核心工作之一就是**构建验证带宽**——它不是单靠 human review，而是一整套体系：

- **判据先于实现：谁控制 spec，谁控制结果。** 先把测试、类型、接口契约固定下来，再让它填实现。Dijkstra 那句老话在 AI 时代更硬：**测试只能证明 bug 存在，永远不能证明 bug 不存在**（出处 1）。而 AI 写的测试有额外偏向——只覆盖它已经想到的路径（事实 2），还可能反过来博弈判据（4.3）。所以判据要么你来定，要么在它写实现之前先独立定下并确认（先测后码的思想源头见出处 9）。
- **信任锚定在外部证据，不锚定在它的语气。** 自然语言的语气不能当作可靠的置信度信号——它可能对错误答案和正确答案一样笃定，还会因为谄媚（4.1）而对你的错误加倍笃定（新一代模型在校准和自我检查上有改善，但"读它的口气"仍不足以当证据）。所以"它说已经验证过了"本身不构成证据；只有能复现的命令、退出码、测试报告、CI 记录、人工检查这些**系统级证据**算数。让它贴证据，不是贴结论。
- **静态分析、lint、类型系统、架构边界**——让尽量多的错误在编译期或部署前暴露，而不是留到线上。

这里给一个能直接用的小工具，把"该不该放手"从感觉变成可算的判断。

**开工前，先估"验证成本"**——决定该不该放手的不是任务难度，是你事后能多便宜地确认它对：

| 问题 | 便宜（可放手） | 昂贵（要盯紧） |
|---|---|---|
| 错误多久暴露？ | 立刻（编译/测试当场红） | 延迟（上线后、特定数据量、并发下才现形） |
| 会不会沉默失败？ | 不会，出错就报错 | 会，结果错了但没有任何报错 |
| 判据客观可复现吗？ | 有确定的 pass/fail | 只能靠人读、靠肉眼看"像对的" |
| 回滚代价多大？ | 一个 revert 搞定 | 数据已变更 / 已对外发出 / 难恢复 |

四个都落在左列 → 放手。任何一个落在右列 → 那一项就是你必须亲自把关的地方。**反直觉之处：越省力生成的代码，越可能落在右列。**

把所有任务按这套标准摊到一张图上，就得到一份"赚 / 陷阱"地图（两根轴是生成成本和验证成本，AI 只压低了前者）：

| 区域 | 特征 | 典型任务 | 姿态 |
|---|---|---|---|
| **赚**：验证便宜且客观 | 判据强、机械、错了立刻现形 | 样板、跨文件重命名、格式化、纯函数的测试、会被丢弃的探索原型、把陌生代码读成一张地图 | 放手，跑判据，扫一眼 |
| **半赚**：验证中等 | 需读关键路径 | 业务逻辑、常规 bug、接口调整 | 盯着用，读关键 diff |
| **陷阱**：验证昂贵或失败沉默 | 依赖全局不变量，错误延迟且安静 | 并发正确性、权限边界、金额/库存/额度、数据迁移、新增依赖 | 它只能帮你看/写/枚举/质疑，判断你来 |

**最诱人放手的地方，往往正是最危险的地方。** 并发和迁移代码，AI 生成起来又快又顺，省下的时间最诱人；而它们恰恰错误代价最高、最难在测试里现形。

### 角色 3：全局不变量的守护者（对应事实 3）

AI 看不到你的系统边界、业务铁律、历史事故教训（事实 3）。你的工作是把这些**不变量显式化**——写进架构约束、接口契约、测试用例，以及给 AI 划禁区的 prompt 里。

> 你脑子里那些"不能违反的规则"，最好的归宿不是留在脑子里，而是变成系统里可执行的约束。只有显式化的不变量，才能同时约束人和 AI。

配一个能直接用的清单——**动手前，先枚举"这个改动碰了哪些全局不变量"**。它既是你自己的检查单，也是该抄进 prompt 的上下文：

- **幂等**：这个操作会不会被重复触发？重复触发结果还对吗？
- **顺序 / 并发**：它依赖执行顺序吗？多个请求同时来会怎样？
- **权限**：谁**不该**能做这件事？测试覆盖了"越权被拒"吗？
- **守恒**：涉及钱 / 库存 / 额度时，有没有"总量不凭空增减"的守恒律？
- **可逆**：出错了能回到原状吗？回滚方案是什么？
- **部分失败**：做到一半挂了会留下什么中间态？

凡是有条目被勾中的改动，就属于事实 3 说的"依赖它看不见的不变量"，判断权必须留在人手里。把勾中的条目直接写进任务描述，是把你的全局视野"借"给它局部视野的最有效方式。

### 贯穿三角色的警觉：自动化 complacency

三副面孔之外还有一条底线。人因工程几十年前就发现（Bainbridge《自动化的反讽》，1983，出处 7）：**越可靠的自动化，越会侵蚀人的监督能力和现场手感，而偏偏在它少数出错的时刻最需要人顶上。** 最危险的不是它常错，是它好到你不再检查。对策是把"检查"变成不依赖你意志力的机制——强制的判据、干净上下文里的独立 review，而不是指望自己每次都保持警觉。

## 六、系统与个体：如何不被 AI 的产能淹没

前面讲的是一个人怎么做。但如果团队里每个人都用 AI，生产带宽真的爆炸了，系统会不会被代码量淹没？答案取决于：**你的系统是否具备"吸收大量代码而不崩溃"的结构。** 而且产能爆炸放大的不只是代码量，还有**安全面**——更多自动生成的代码、更多 agent 直接执行的命令、更多顺手引入的依赖，每一样都是新的风险入口。

### 系统层面

- **架构就是验证带宽的放大器。** 好的架构让每段新代码的影响范围可控，让验证成本与代码量线性相关而非指数相关。模块化、边界清晰、依赖方向明确——这些旧原则在 AI 时代反而更重要，因为它们在压小 AI 生成代码的"爆炸半径"。
- **拒绝复杂度优先于生成功能。** AI 让你能很快加功能，但最快的往往是往系统里塞更多东西。驾驭复杂度的最高形态，是对新复杂度说不；判断"什么不该做"比"什么能做"更值钱。
- **建立团队级验证规范**：统一的生成约束（让 AI 产出可预测）、统一的测试标准（防止伪造验证）、明确的高风险清单（哪些地方 AI 生成后必须人工走查）。

### 安全护栏：产能放大的是攻击面，不只是代码量

前面的"验证"守的是**正确性**；这里守的是**安全性**——两者是不同的失败模式，一段验证通过、行为完全正确的代码，仍然可能是不安全的。coding agent 的外壳（事实 1 里说的工具、命令执行、权限）在提效的同时，也把攻击面撑大了。至少要有这几道护栏（LLM 应用侧的系统性风险清单见出处 6，OWASP Top 10 for LLM Applications 2026）：

- **密钥与敏感数据**：secret、凭证、客户数据一旦进入 prompt，就进入了模型供应商 / 工具链的处理边界，可能被日志、缓存、审计或插件链路接触（具体取决于各家的数据保留与隔离策略）。脱敏或构造最小复现再给；CI 里加 secret 扫描，别只靠人自觉。
- **prompt injection**：当 agent 会读取外部内容（网页、issue、依赖的 README、日志），这些内容里可能藏着指令，诱导它执行计划外操作。把外部内容当**不可信输入**，对能产生副作用的动作设确认点。
- **依赖与供应链**：模型会推荐不存在的（幻觉包，事实 1 的 5.2%/21.7%）、仿冒的或过时不安全的包——这正是 typosquatting / 依赖混淆的温床。新增依赖必须人工确认存在、来源可信、许可证与安全记录 OK，并检查 lockfile 与传递依赖。
- **过度代理权限（Excessive Agency）**：别给 agent 超出任务所需的自主权。它能自动执行的动作范围、能调用的工具、能触及的系统越大，一个错误决策能造成的破坏就越大——这是 OWASP 单列的一类 LLM 风险（2026 版 LLM03）。按"完成这个任务真正需要什么"来授权，而不是"图省事全开"。
- **命令执行与权限**：给 agent 的权限按最小化给；危险命令（删除、迁移、对外请求、改权限）设人工确认；默认不放开生产凭证。
- **生产环境隔离**：agent 的读写默认限制在开发/测试环境；触碰生产数据、执行数据迁移要走人工审批，而不是让它自己跑。

这些护栏大多**不能靠模型自觉**，得做成流程和工具（扫描、沙箱、审批门、权限最小化）——和第五节"把检查变成不依赖意志力的机制"是同一个道理。

**一句时效性判断：别把这些理解成"模型再强一点就会消失"。** 幻觉包、prompt injection、权限误用、谄媚、多步漂移，到 2026 年都没有被彻底克服——USENIX Security 2025 那项研究就把包幻觉描述成对软件供应链的实质性、需要紧急关注的威胁（出处 3）。更准确的说法是：工具层护栏在快速变强（沙箱、权限分级、审批门、注入探针），但风险重心从"模型自己犯错"转移到了 agent 权限、上下文污染、供应链和验证流程。护栏是把问题**控制住**，不是让它消失。

### 个体层面：什么能力会越来越稀缺

如果生产带宽被拉满，稀缺的就不再是"写得快"，而是：

- **判断力**：在多版本输出里快速识别哪个对、哪个是地雷；
- **系统感**：对全局不变量和失败模式的积累；
- **验证设计能力**：设计出高效、且独立于生成通道的验证方案；
- **复杂度治理能力**：在增长压力下保持系统简洁。

这些能力有个共同点：**都不能被快速生成，只能靠时间和实践积累。** AI 时代的讽刺正在于此——生产代码越容易，真正稀缺的能力就越贵。

## 七、诚实的反面：这些原理何时不适用

一套只会加码、从不喊停的方法论是可疑的。上面的原理都有边界：

- **何时该让上下文累积。** "两轮不对就重开"针对的是"上下文被失败尝试污染"。但当你在深挖同一个复杂问题、前面的探索历史本身就是线索时，清空反而丢掉价值。Anthropic 官方文档也直说：有时你**应该**让上下文累积（出处 8）。判断标准是"历史里的信息还有用吗"，不是"聊了多少轮"。
- **"当假设看待"何时过度。** 对可丢弃的探索原型、一次性脚本，验证成本≈0（跑一下看结果就行），这时逐行审查是浪费。原理是"验证成本决定投入"，而不是"一切都要重审"。
- **过度审查会制造 over-engineering。** 一个被要求"找问题"的 reviewer（无论人还是模型）几乎总能找出问题，即使代码本没问题——于是你被推着加防御性代码、加不可能发生分支的测试。连 Claude Code 官方文档都专门警告这点：让 reviewer 只报影响正确性或需求的缺口，其余当可选（出处 8）。审查是为了可信，不是为了显得尽责。
- **谄媚的反面：有时你恰恰需要它反驳你。** 它默认附和（4.1），所以当你想压力测试自己的方案时，得**明确要求它扮演反方**（"找出这个设计会失败的三种情形"），否则你只会听到自己想法的回音。

原理是透镜，不是戒律。理解它为什么成立，你才知道它什么时候不成立。

## 八、收束

把整条链收成一句：

> AI 的本质决定了它能极大放大生产带宽，却远不能同等地放大"建立独立确信"的验证带宽；这两者的剪刀差，把工程瓶颈从"写"推到了"验"；工程师的新定位，就是围绕"验"重建能力——精确表达意图、构建验证体系、守护全局不变量；而系统的存亡，取决于有没有足够的架构约束与安全护栏去吸收 AI 的生产力，而不被它淹没。最终，生产代码越容易，判断力、系统感、验证设计和复杂度治理就越稀缺、越值钱。

不必背任何清单，三个事实各自推出一条主线就够了：

- 它是概率分布 → 它给的是假设，要验证，要用你的上下文把它从"主流中位数"拉到"你的系统"；它还会谄媚、会博弈判据，因为它优化的是"讨好"和"达标"，不是"正确"。
- 生成变便宜、"确信它对"没同步变快 → 瓶颈是验证，所以拆小、判据先行、证据大于语气、回合要短。
- 它只有局部视野 → 凡是依赖全局不变量的改动，判断权必须留在人手里，而你能做的是把那些不变量显式借给它。

> AI 编码的目标，不是让代码来得更快，而是让你能干净地把**生成**和**验证**分开——把便宜的生成尽量交给它，把昂贵的判断牢牢留给自己。**工具越强，越需要有人知道：在哪里用，何时收手，以及为什么。** 速度是副产品；可信才是目的。

- 文中所有"它倾向于……""它容易……"，都是**当前这一代工具上的常见行为**，会随模型、版本、prompt 和工具脚手架变化，不是"AI"这一类别的永恒属性。请当作"不能依赖它不犯的错"，而非"它一定会犯的错"。
